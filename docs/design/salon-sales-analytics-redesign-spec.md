## Target User

미용실 원장 한 명. 데이터 분석가가 아니다.
하루 영업이 끝난 뒤, 혹은 손님이 끊긴 사이에 **1~2분** 본다.
알고 싶은 것은 "장사가 잘 되고 있나"이지 "지표 간 상관관계"가 아니다.

## Salon Domain

- 1인 샵 (실측: `operator` 서승애 단일).
- 화요일 정기 휴무 (실측: 2026-07 화요일 0건).
- 금·토 피크 (실측: 23건 · 21건).
- 재방문 위주 (실측: 2026-07 고객 72명 중 신규 4명).
- 객단가 편차가 크다 (실측 p50 ₩18,000 · p90 ₩90,000) — 커트와 펌·매직이 한 원장에 섞인다.

## User Questions (화면이 답해야 할 질문)

1. 이번 달 얼마 벌었나? 지난달보다 나은가?
2. 손님이 언제 오나? (요일·시간)
3. 새 손님이 오고 있나, 단골로만 버티나?
4. 한 사람당 얼마 쓰고 가나?
5. 실제로 내 손에 남는 돈은 얼마인가?

## Existing Data

인벤토리 A·B군만 쓴다. C군(원가·예약·연령·담당자)은 화면에 만들지 않는다.

## Selected Direction — A (원장 브리핑형)

3안 비교 (1~5점, 높을수록 좋음):

| 축 | A 브리핑형 | B 균형 대시보드 | C 질문 중심형 |
|---|---|---|---|
| 10초 이해 | **5** | 3 | 4 |
| 30초 이해 | **5** | 4 | 4 |
| 미용실 업종 적합성 | **5** | 3 | 4 |
| 분석 지식 요구 (낮을수록 좋음) | **5** | 2 | 5 |
| 반복 사용성 | 4 | **5** | 2 |
| 정보 과부하 회피 | **5** | 2 | 4 |
| mobile | 3 | 3 | 4 |
| accessibility | 4 | 4 | 4 |
| backend feasibility | **5** | 4 | 3 |
| implementation complexity (낮을수록 좋음) | 4 | **5** | 2 |
| future extensibility | 4 | **5** | 3 |
| **합계** | **49** | 40 | 39 |

**A 채택.** 결정적 이유는 취향이 아니라 데이터다 — 시술·결제수단이 원본에서 비어 있어
B(카드·차트를 늘리는 방향)는 빈 카드가 화면을 채운다. A는 문장이 먼저 오므로,
보여줄 것이 없을 때 **"없다"고 말할 자리**가 구조 안에 있다.

Trade-off: A는 insight 문장이 틀리면 곧바로 거짓말이 된다. 그래서 §Insight Rules 를
테스트로 고정한다 (`lib/salon-briefing.test.ts`).

## IA (위에서 아래로)

```
탭 (매출 분석 · 결제 등록 · 지출/정산)
기간 컨트롤 (일·주·월·연·누적 + ← →)
설명 + 인쇄/CSV
─────────────────────────────
[1] 브리핑 한 줄        ← 이 화면의 답
[2] KPI 4칸             ← 답의 근거 숫자
[3] 주 차트 (전폭 1행)   ← 답의 추이
[4] 요일 · 시간 · 누가 왔나 (3열)
[5] 결제 수단 · 시술 · 정산
```

`[1]` 이 없으면 `[2]` 부터 시작해도 화면이 성립해야 한다 (briefing prop optional).

## KPI

넷만 둔다. VAT·지출은 `[5]` 정산 표가 아홉 줄로 이미 보여준다.

| 카드 | 값 | 보조 문구 |
|---|---|---|
| 총 매출 | `SUM(gross_won)` | 비교 라벨 + 증감% (또는 `–`) |
| 실결제 | `SUM(amount_won)` (지출 제외) | "할인·포인트를 뺀 금액" |
| 샵 수익 | `SUM(profit_won)` | "VAT·수수료·지출을 뺀 금액" |
| 객단가 | 총 매출 ÷ 결제 건수 | "총 매출 ÷ 결제 건수" |

## Metric Definitions

`docs/redesign/C-revenue-definition.md` 의 어휘를 그대로 따른다.
라벨은 **"총 매출"** 로 고정한다 — 매출액·총액·판매액을 섞지 않는다.

## Comparison Rules

1. 비교 대상이 없으면 비교하지 않는다.
2. 직전 기간이 `null` 또는 `0` 이면 `null` 을 반환한다. `+∞%` 가 나올 경로를 만들지 않는다.
3. **진행 중인 기간은 지난 기간을 같은 날짜까지 잘라 견준다.** 8/1–8/12 ↔ 7/1–7/12.
   그리고 잘랐다는 사실을 라벨과 문장이 함께 밝힌다: `지난달 같은 기간(12일까지)`.
4. 1% 미만 변화는 추세로 부르지 않는다 — "거의 같습니다".
5. 색은 방향에만 쓰고, 방향과 함께 **단어**를 항상 적는다 (색만으로 증감을 말하지 않는다).

## Insight Rules

문장은 서버가 만든다. 화면은 조립하지 않는다.
전부 `lib/salon-briefing.ts` 에 있고 테스트로 고정한다.

- 결제 0건 → "이 기간에는 결제 기록이 없습니다." (₩0 이 늘었다/줄었다고 말하지 않는다)
- 비교 불가 → "…벌었습니다. 지난달에 견줄 기록이 없어 증감은 표시하지 않습니다."
- 붐빈 요일/시간 → "금요일이 가장 붐빕니다 — 23건." + 방문 0인 요일을 이어서 밝힌다.
- 한글 조사(이/가)는 받침으로 고른다. "14시이" 같은 문장을 내지 않는다.

## Service Analysis

`details.serviceMajor` 기준 가로 막대. 유형이 하나뿐이면 막대 대신 사실을 쓴다
("이 기간의 유일한 유형입니다") — 항상 100%인 막대는 정보가 아니다.

## Time Analysis

- 요일: **일~토 일곱 칸 고정.** 0건 요일을 빼지 않는다 — 빈 칸이 곧 휴무 정보다.
- 시간대: 손님이 온 시간만. 영업시간을 모르므로 0~23시를 지어내지 않는다.
- **히트맵을 쓰지 않는다.** 요일 × 시간 교차는 1인 샵 한 달 표본(89건)에서 칸당 1~2건이라
  색 농담이 잡음이 된다. 두 축을 각각 막대로 나눠 보여주는 편이 정확하다.

## Customer Analysis

방문 / 다녀간 고객 / 이번이 첫 방문 / 재방문 고객 비중 / 객단가.

- 신규 = 고객별 `MIN(occurred_at)` 이 기간 안. **`details.visitType` 을 쓰지 않는다** (전 행 `repeat`).
- **"재방문율"이라는 말을 쓰지 않는다.** 코호트 추적이 아니다.

## Staff Analysis

**만들지 않는다.** 1인 샵이다 (인벤토리 §2).

## Reservation Analysis

**만들지 않는다.** 이 DB에 예약 데이터가 없다 (`records` 에 `bookings` kind 부재).

## Empty / Sparse

| 상황 | 화면 |
|---|---|
| 기간에 결제 0건 | 브리핑이 "결제 기록이 없습니다", 객단가 `–`, 증감 `–` |
| 직전 기간 0원 | 증감 `–` (0%가 아니다) |
| 요일/시간 표본 없음 | "…별로 나눌 방문 기록이 없습니다." |
| 유형이 하나뿐 | 막대 대신 "이 기간의 유일한 …입니다" |
| 아직 안 온 날 | 막대 없음 (`state: future`) — ₩0 과 구분한다 |

## Responsive

기준 1440, 최소 1280 (`docs/redesign/E-dashboard-design.md` 승인 사항).
브리프 §83은 모바일을 요구하나 **승인된 설계가 우선**한다 (소스 오브 트루스 순서).
375/768은 가로 스크롤이 남으며, 이는 이 화면만의 문제가 아니라 셸 전체의 성질이다 —
별도 작업으로 잡는다. 이번 범위에서 **새 파손을 만들지 않는 것**까지가 목표다.

## Accessibility

- 모든 차트에 `sr-only` `<table>` 대체 텍스트.
- 포커스 링 2px, 모든 탭 스톱에서 보인다.
- `prefers-reduced-motion` 이면 막대 transition 제거.
- 증감을 색으로만 말하지 않는다 (부호·단어 병기).
- 요일/시간 막대는 장식이 아니라 값이므로 표로도 읽힌다.

## Backend Dependencies

새로 만든 것 셋. 전부 SQL 집계이고 프런트는 다시 세지 않는다.

- `weekdayLedger(start, endExclusive)`
- `hourLedger(start, endExclusive)` — 서울 시각으로 묶으려 `'+9 hours'`
- `customerMixLedger(start, endExclusive)` — 신규는 전체 원장 최초 방문 기준

**SQL 스키마는 바꾸지 않는다.**

## Non-goals

- 이익률 · 순이익 (원가 데이터 없음)
- 예약 · 노쇼 · 전환율 (데이터 없음)
- 연령대 (생년월일 없음)
- 담당자별 (1인 샵)
- 히트맵 · 3D · 레이더 · 게이지 · 이중 축 · 도넛 여러 개
- 차트 라이브러리 추가

## Acceptance Criteria

1. 10초 안에 "이번 기간 얼마 벌었고 지난 기간보다 어떤지" 읽힌다.
2. 진행 중인 달에서 증감이 착시로 부풀지 않는다 (같은 날짜까지 잘라 비교, 그 사실 명시).
3. 어떤 기간을 골라도 `+∞%` · `NaN` · `-Infinity` 가 화면에 나오지 않는다.
4. 빈 기간에서 모든 칸이 "없다"고 말한다 (0으로 속이지 않는다).
5. 요일 축은 언제나 일곱 칸이다.
6. "재방문율" 이라는 문자열이 화면에 없다.
7. 1440·1280에서 가로 오버플로가 없다.
8. 모든 탭 스톱에 포커스 링이 보인다.
9. `prefers-reduced-motion` 에서 막대 애니메이션이 없다.
10. `tsc --noEmit` · `vitest run` 전부 통과.
