매출 화면 수정 명세

인쇄·설정 제외. 파일과 줄 번호까지 지정한 실행 명세.

범위 밖 — 인쇄(이미 제거됨), 설정 화면(다른 세션 작업 중), 문자 자동 규칙(별도 판단).

측정 기준 — .data/hairhaeyo.sqlite, 원장 5,578행. 브라우저 실측은 다른 세션이 Playwright를 점유해 코드·DB로만 확인했다.

작업 1 · 정산표가 없는 것을 뺐다고 말한다

측정

SELECT SUM(gross_won), SUM(discount_won), SUM(points_won),
       SUM(amount_won), SUM(vat_won), SUM(fee_won),
       SUM(expense_won), SUM(profit_won)
FROM ledger WHERE kind='payment';

총 매출   291,865,150
할인               0     ← 전부 0
포인트 사용  1,450,792
실결제    291,865,150     ← 총 매출과 완전히 같다
VAT            2,727     ← 5,578건 중 1건
결제 수수료  5,243,451     ← 유일하게 실재
지출               0     ← 0건
샵 수익   286,701,972

화면은 샵 수익 = 실결제 − VAT − 결제 수수료 − 지출 이라 적는다. 네 항목 중 실재하는 것은 수수료 하나다. 원장이 이 숫자를 자기가 번 돈으로 읽는다 — 임대료·재료비·인건비가 하나도 안 빠졌다.

덤으로 찾은 것: 화면 수식과 저장값이 ₩83,000 어긋난다. amount_won = 0 인데 profit_won > 0 인 이관 행이 5건 있다(예: hairnury-detail-514328-3 — 결제 0원, 수익 4,850원). 이번 명세에서 고치지 않는다. 5,578건 중 5건이고 원본이 그런 것이라 화면이 만든 문제가 아니다. 별도로 다룬다.

수정 2-1 · 분 단위 다양성을 근거로

lib/salon-store.ts:503-515 
hourLedger(start: string, endExclusive: string) {
  return db.prepare(`
    SELECT CAST(strftime('%H', firstAt, '+9 hours') AS INTEGER) AS hour,
           COALESCE(SUM(gross), 0) AS gross,
           COUNT(*) AS count
           COUNT(*) AS count,
           COUNT(DISTINCT strftime('%M', firstAt)) AS minutes
    FROM ( ... )
    GROUP BY hour ORDER BY hour
  `).all(start, endExclusive) as LedgerHourRow[];
}
lib/salon-domain.ts (LedgerHourRow) 
export type LedgerHourRow = {
  readonly hour: number;
  readonly gross: number;
  readonly count: number;
  /** 이 시간대에 등장한 서로 다른 '분'의 개수. 시각이 진짜 기록됐는지 판정한다. */

};
lib/salon-briefing.ts:73-75 
/**
 * 시각이 진짜인지는 "칸이 몇 개인가"로 알 수 없다.
 *
 * 이관 자료는 원본에 시각이 없어 날짜만 읽고 정오로 채운다
 * (`scripts/import-hairnury-details.mjs:9`). 그러면 시간대 분포가 생기긴 하는데
 * 그건 손님이 온 시각이 아니라 가져오기가 만든 모양이다 — 실측으로 아홉 칸이
 * 전부 279의 배수였고 5,578행 중 5,577행의 분이 :00 이었다.
 *
 * 사람이 찍은 시각은 분이 흩어진다. 그것을 근거로 삼는다.
 */
export function isUsableHourPattern(rows: readonly LedgerHourRow[]) {
  return rows.filter((row) => row.count > 0).length > 1;
  const live = rows.filter((row) => row.count > 0);
  return live.length > 1 && live.some((row) => row.minutes > 1);
}

이게 기능 삭제가 아닌 이유. 실제 결제가 쌓이면 분이 흩어지고 시간대 분석이 저절로 되살아난다. 화면 코드는 한 줄도 바꾸지 않는다 — revenue-dashboard.tsx:540이 이미 availability.hour === false일 때 UnavailableAnalysisCard를 그린다. 그 카드가 "가져온 기록에 이 분석에 필요한 정보가 없습니다"라고 말한다. 정확히 지금 사실이다.

작업 5 · 운영 현황의 결제 진입

Codex 안에 동의한다. 다만 "완료됐지만 결제 없으면 결제 필요"는 과거 데이터에 적용하면 안 된다.

booking.ts:7의 상태는 confirmed | waiting | completed. "완료인데 결제 없음"을 판정하려면 예약↔원장을 이어야 하는데, 원장 행에 bookingId가 붙는 것은 payment-form.tsx에 booking prop이 생긴 최근 변경 이후다. 과거 5,578행에는 없다.

과거 예약까지 훑으면 모든 옛 예약이 빨갛게 물든다.

인쇄는 이미 제거됐다. 문서에 제거 사실만 남긴다 — 지우지 않는 이유는 원본 프로그램의 기능 목록이 추적 가능해야 하기 때문이다.
