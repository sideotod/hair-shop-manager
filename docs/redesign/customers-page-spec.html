1. 대기 등록 · 대기 고객 박스 제거 요구 1, 8

예약에는 이미 status: "waiting" 이 있다(lib/booking.ts:7). 대기 고객은 같은 개념의 두 번째 저장소였고, 예약을 저장하면 대기 행을 archive 하는 연결 코드까지 붙어 있었다.

제거 이유: 개념이 두 벌이면 "오늘 대기 몇 명"이라는 질문에 답이 둘 나온다. 대기 손님은 시간이 정해지지 않은 예약이므로 예약 하나로 표현된다.

지우는 것

  • /customers 의 대기 고객 박스, 대기 등록 팝업(?waiting=1), 대기 완료 버튼
  • 대시보드 대기 고객 박스, 빠른 작업 "대기 등록", 빈 시간 문구의 "대기 고객 N명 배정 가능"
  • 서버 액션 saveWaitingCustomer, completeWaitingCustomer 와 lib/customer-operations.ts 의 두 함수
  • 고객 등록 폼의 "대기 고객 동시 등록" 체크와 대기 메모
  • saveBookingRecord() 안의 waitingId archive 분기, 예약 폼의 waitingId hidden 필드

DB

  • waiting-customers 행은 현재 0건이고 이를 가리키는 감사 이력도 0건이다. 화면과 코드가 사라지면 아무도 안 읽는 kind 가 되므로 정리 스크립트에서 DELETE 한다.
  • RecordKind 유니온에서도 "waiting-customers" 를 뺀다 — 남겨두면 다시 쓸 수 있는 것처럼 보인다.

기준 금액은 실결제액(할인·포인트사용 뺀 뒤)이다. 정가에 적립하면 할인 쿠폰이 포인트로 되돌아온다.

잔액 계산은 그대로: 적립 비율만 설정이 정하고, 적립 결과는 여전히 details.pointsEarnedWon 을 실은 원장 행이 만든다(salon-store.ts:302). 잔액을 두 곳에서 계산하지 않는다.

비회원은 적립 불가 규칙(finance.ts:124)이 그대로 이긴다 — 자동 채움도 비회원이면 0.

DB 정리

scripts/prune-customer-fields.mjs 를 새로 만든다. 이 파일 하나가 이번 재설계의 모든 DB 정리를 담는다 — 쓰지 않는 필드 삭제, 대기 고객 kind 삭제, 보관 해제. 전부 json_remove / DELETE / UPDATE 라서 스키마 변경은 없다(payload 는 JSON 열이다).

-- 1) 쓰지 않는 고객 속성 영구 삭제
UPDATE records SET payload = json_remove(payload,
  '$.grade','$.group','$.motive','$.birthday','$.birthdayCalendar',
  '$.telephone','$.phoneAbsent','$.pointCard','$.familyNumber','$.nickname',
  '$.address','$.email','$.pointDebtWon','$.lastServiceAt','$.firstMetAt'
), updated_at = updated_at
WHERE kind = 'customers';

-- 2) 대기 고객 — 화면이 사라지므로 행도 지운다 (§1)
DELETE FROM records WHERE kind = 'waiting-customers';

-- 3) 보관 해제 — 되돌릴 화면이 없어 기능을 없앤다 (§10)
UPDATE records SET archived_at = NULL
WHERE kind = 'customers' AND archived_at IS NOT NULL;

VACUUM;

updated_at 은 일부러 그대로 둔다 — 값을 지운 것이지 고객 정보가 바뀐 것이 아니다. 실행 전 .data/hairhaeyo.sqlite 사본을 뜬다. audit_events 는 손대지 않는다 — 무엇을 언제 지웠는지가 거기 남아야 한다.

선결제

customers.value.prepaidWon: number  // 0 이상 정수, 기본 0

등록 시 0보다 크면 원장에 결제 1행을 남긴다.

kind: "payment", amountWon: 충전액, customerId,
details: { operator: "원장", serviceMajor: "선결제", prepaidChargeWon: 충전액,
           paymentMethods: { cash: 충전액 } }
원장에도 남기는 이유: 100만원을 긁은 그 날 100만원이 실제로 들어온다. 고객 필드만 바꾸면 그 돈이 매출 화면에 영영 안 잡히고, 나중에 시술로 차감할 때도 매출이 안 잡혀 100만원이 장부에서 통째로 사라진다. 잔액은 고객 필드가 보관하고, 돈이 움직인 사실만 원장이 기록한다.

차감은 결제 팝업에서 PAYMENT_METHODS 에 prepaid: "선불권" 을 추가해 처리한다. lib/revenue-data.ts:7 이 이미 이 이름을 알고 있고, 시드 데이터에도 paymentMethods.prepaid 행이 있다. 결제 저장 시 prepaidWon 을 그만큼 줄이고, 잔액보다 크면 거절한다.

const outside = (event: PointerEvent) => {

계산을 다시 적지 않는다: 금액 파생은 settleAmounts() 를 그대로 부른다(lib/settlement.ts). 산식을 여기에 옮겨 적으면 두 벌이 되고, 언젠가 갈라져 "화면 합계는 맞는데 저장은 실패"가 된다.

저장 후 /customers?customer=<id>&notice=… 로 복귀. payment-actions.ts 의 returnTo 화이트리스트에 /customers 를 추가해야 한다(현재 /sales 만 허용).

선결제 충전 팝업

금액 + 결제수단 + 날짜 3칸. 저장하면 prepaidWon 증가 + 원장 1행.

고객 보관 — 기능 자체를 삭제

확인 팝업을 만들지 않는다. 보관 기능을 없앤다. 되돌리는 화면이 없는 단방향 버튼이기 때문이다.

왜 팝업이 아니라 삭제인가: 보관을 누르면 고객이 목록에서 사라지고, 되돌릴 방법이 프로그램 안에 없다. 문구로 경고하는 것은 "실수하면 복구 못 합니다"라고 알려주는 것일 뿐 실수를 되돌려주지 않는다. 지울 일이 정말 있으면 그때 보관 목록과 복원 버튼을 한 벌로 만든다. 반쪽만 있는 기능은 없느니만 못하다.
